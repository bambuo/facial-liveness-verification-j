## 1. 验收环境与方法

当前仓库没有实现代码，本轮只做文档与设计评审，不能进行功能验收。后续验收环境：

| 项       | 要求                                                                                   |
|----------|----------------------------------------------------------------------------------------|
| 操作系统 | 生产 Linux x64 或 arm64（glibc，eclipse-temurin 基础镜像）；开发可在 macOS             |
| 运行时   | JDK 25（Temurin，最低标准）+ JetBrains Kotlin Toolchain CLI（Alpha）                   |
| 数据库   | PostgreSQL 16+，安装 pgvector                                                          |
| 缓存     | Redis 7+                                                                               |
| 人脸引擎 | mica-ai-face（YuNet + SFace + MiniFASNetV2，模型路径 `mica.ai.face.model.*` 显式配置） |
| OCR      | mica-ppocr（PP-OCR ONNX 模型）                                                         |
| 对象存储 | 本地 RustFS（docker compose）；线上 Cloudflare R2                                      |
| 客户端   | 浏览器 `localhost` 或 HTTPS；RN 0.74 / Expo 51                                         |
| 测试数据 | 脱敏或明确授权的真人样本，禁止把真实证件图提交到仓库                                   |

验收方法：全部验收项直接在真实引擎（mica-ai-face + 模型文件）下执行——先以 `dev` profile 打通 JWT、challenge、上传、审计与
H5，再用真实（脱敏授权）样本执行 AC-04～AC-09，最后用真实业务样本校准阈值。实现中不存在 Mock 引擎；任何模拟结果不得作为验收依据，模型路径缺失启动即失败。

## 4. v2 最小链路冒烟记录（2026-11-14，macOS + 真实 mica-ai-face 引擎）

- 构建：`kotlin build` 通过（KT 0.13.0，运行于工具自动 provision 的 JDK 25.0.5）。
- 启动：dev profile 2.4s，模型三件套加载成功，`/actuator/health` UP。
- 正链路：dev token → challenge(enroll) → enroll（样例人脸图）→ challenge(verify) → verify 同图
  `passed, score=1.0, liveness=real`，签发 HS256 结果令牌（含 jti，5 分钟）。
- 负链路：设备绑定不一致 409 `CHALLENGE_REPLAY`；未录入 404 `FACE_NOT_ENROLLED`；challenge 重放 409 `CHALLENGE_EXPIRED`。
- 结论：AC-03（跨设备/重放）、AC-04（无状态 1:1，Mock 之外的真实引擎同图口径）、AC-06（档案 1:1）在最小口径下通过；其余 AC 仍按第 2
  节状态执行。

### v2.1 增量（2026-11-14，主动动作活体 + 浏览器真人实测）

- 逐动作门控：页面持续采帧并周期性调用 `/v1/action-check` 预检，服务端确认该动作完成后才进入下一个；单动作 15s
  超时即失败并指名动作；张嘴判定基线取 straight 段帧（修复过"基线仅首次携带导致卡住"的缺陷）。
- 浏览器真人实测（用户操作）：录入 → 依次完成正视/转头/张嘴 → 认证通过，`score=0.7508、liveness=real`，结果令牌签发——真实重拍同人分数落在
  0.75（远超 0.35 阈值、低于同图 1.0），引擎区分度符合预期。
- 修复记录：前端抓帧镜像矩阵错误（上传空白帧致 NO_FACE）、MP uuid 列类型、KT 模块发现/依赖语义等，见实施方案 §11 与会话记录。

## 5. 发现并修复的问题

- KT 未自动发现子目录模块 → `project.yaml` 显式 `modules` 列表。
- MP 3.5.9+ 拆包：租户拦截器需 `mybatis-plus-jsqlparser`；KT 默认 SB 4.1.1 → 模块级钉 3.5.7。
- PG uuid 列 vs varchar 参数 → JDBC URL `stringtype=unspecified`。
- MP 实体不能用 record（无 getter/空构造）→ 转 POJO；KT 依赖默认不 exported → jjwt-api 标记 exported。
- 多进程残留导致 8080 被旧实例占用（pkill -f 匹配不到 KT 的 java 子进程，需按 PID 处理）。
- 其余待确认项见实施方案第 13 节。

## 8. 复现步骤

1. 准备 JDK 25 与 Kotlin Toolchain CLI，创建 `project.yaml` + 各模块 `module.yaml` 骨架；Linux/Docker 准备 PostgreSQL +
   pgvector、Redis、RustFS、模型与 OCR 模型。
2. 执行 `docs/需求/0001/sql/` 下的 DDL（或 compose 初始化脚本）。
3. 配置 `mica.ai.face.model.*` 模型路径，以 `SPRING_PROFILES_ACTIVE=dev`、`AUTH_MODE=dev-token`、
   `AUTH_ENABLE_DEV_TOKEN=true` 启动（真实引擎）。
4. 打开 `http://localhost:8080/dev/face-test.html`，完成 enroll 与 verify。
5. 用授权样本重复 AC-04 至 AC-09。
6. 运行 `kotlin build`、`kotlin test`、两个文档校验脚本与 Mermaid 渲染，记录实际输出。
7. 按 AC-01 至 AC-14 逐项填写结果；未执行项保留“未执行”。
