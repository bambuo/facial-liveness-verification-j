# 01 项目架构

> 文档编号：01
> 项目：人脸核验平台
> 状态：设计稿，待评审
> 证据基线：技术栈切换评审（2026-11-14，Spring Boot + mica-ai-face），尚无实现代码

## 1. 定位

平台是独立部署的人脸核验能力服务，不绑定具体业务用户体系。业务侧只依赖 API、短期 JWT 和统一采集组件，平台负责采集后的活体、1:
1、1:N、证件 OCR、阈值与审计。

## 2. 组件职责

| 组件               | 职责                                                                              | 不负责                 |
|--------------------|-----------------------------------------------------------------------------------|------------------------|
| `face-service-api` | HTTP 路由、JWT 验签、租户解析、限流、参数校验、OpenAPI（Spring Boot MVC）         | 业务用户登录、业务放行 |
| `application`      | Match/Enroll/Verify/Liveness/Identify/Document 用例编排、事务、幂等               | 直接操作 ONNX 模型     |
| `domain`           | 实体、值对象、策略接口、`FaceEngine`、`FaceIndex`、`DocumentRecognizer`           | 外部 I/O               |
| `infrastructure`   | mica-ai-face、pgvector、mica-ppocr、MyBatis-Plus、Redis、密钥库（落库）、对象存储 | 业务规则               |
| `worker`           | 异步任务、过期清理、留存清理、索引重建、模型版本迁移                              | 同步请求链路           |
| `contracts`        | DTO、错误码、OpenAPI 契约                                                         | 业务实现               |
| `dev H5`           | 本地采集与联调页面，仅 dev profile                                                | 生产入口               |

### 2.1 包结构与命名

Kotlin Toolchain 多模块（项目级 `project.yaml` + 各模块 `module.yaml`），单一根包 `faceservice`（正式 groupId/包名落地时按公司规范调整）：

| 模块                          | 根包                         | 典型类型                                                                                                                                               |
|-------------------------------|------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------|
| `face-service-api`            | `faceservice.api`            | `DevTokenController`、`ChallengeController`、`ActionCheckController`、`EnrollmentController`、`VerificationController`、JWT 过滤链（限流未启用）       |
| `face-service-application`    | `faceservice.application`    | `MatchService`、`EnrollService`、`VerifyService`、`LivenessService`、`IdentifyService`、`DocumentService`                                              |
| `face-service-domain`         | `faceservice.domain`         | `FaceEngine`、`FaceIndex`、`DocumentRecognizer`、`ObjectStorage`、`KeyStore`、实体与值对象                                                             |
| `face-service-infrastructure` | `faceservice.infrastructure` | `MicaFaceEngine`、`DbKeyStore`、`AesGcm`、`*Mapper`、`*Entity`、租户拦截器（`PpocrDocumentRecognizer`/`PgFaceIndex`/`S3ObjectStorage` 随对应路由批次） |
| `face-service-worker`         | `faceservice.worker`         | 队列消费者、`@Scheduled` 清理任务、索引重建                                                                                                            |
| `face-service-contracts`      | `faceservice.contracts`      | DTO（record）、`ErrorCode` 枚举、OpenAPI 描述                                                                                                          |

- 实现类按底层技术命名（如 `MicaFaceEngine` 实现 `FaceEngine`），Javadoc 标注所实现的接口与模型版本。
- 配置属性用 `@ConfigurationProperties` record 统一绑定：`AuthProperties`、`FaceProperties`、`StorageProperties`、
  `RetentionProperties`。

## 3. 启动顺序

1. 读取配置并校验生产安全约束：生产环境不得启用 `auth.enable-dev-token=true` 或 `auth.mode=dev-bypass`。
2. 连接 PostgreSQL 与 Redis；检查 pgvector 扩展与向量维度（SFace 为 128d）。
3. 校验模型文件与许可证文件，加载 mica-ai-face（YuNet/SFace/MiniFASNetV2）与 mica-ppocr 模型；路径未配置或文件缺失时启动失败。
4. 预热人脸检测、特征提取、活体与 OCR 会话；就绪探针在预热完成后才返回成功。
5. 启动 API 与 Worker；注册健康探针与指标。

任一步失败都应快速失败并输出可定位日志，不带病提供服务。

## 4. 核心抽象

```java
public interface FaceEngine {
    List<FaceDetection> detect(byte[] image);
    float[] extractLargest(List<byte[]> frames);   // 多帧选最大人脸提特征
    LivenessVote checkLiveness(List<byte[]> frames); // 多帧静默活体投票
    List<FrameMetric> analyze(List<byte[]> frames);  // 主动动作几何指标（v2.1）
    double compare(float[] left, float[] right);
    String modelVersion();
}

public interface FaceIndex {
    void upsert(String tenantId, String galleryId, String subjectId, float[] embedding, String modelVersion);
    List<FaceCandidate> search(String tenantId, String galleryId, float[] embedding, int topK);
    void delete(String tenantId, String subjectId);
}

public interface DocumentRecognizer {
    DocumentResult recognize(byte[] image, String documentType);
}

public interface ObjectStorage {
    void put(String key, InputStream content, String contentType);
    void delete(String key);
    String createPresignedGetUrl(String key, Duration ttl);
}

public interface KeyStore {
    byte[] currentKey(String tenantId); // 首次访问自动生成并落库，主密钥包裹
}
```

- `FaceEngine` 首期由 `MicaFaceEngine` 实现（包装 mica-ai-face 的 `FaceDetector`/`FaceAligner`/`FeatureExtractor`/
  `LivenessDetector`/`FaceVerifier` Bean）；不提供 Mock 实现，测试在测试代码内用 Mockito stub 接口；后续可整体替换其他引擎。
- `FaceIndex` 首期由 `PgFaceIndex` 实现（MyBatis-Plus Mapper + 向量 TypeHandler，`vector(128)` cosine HNSW），规模化后可替换
  Qdrant/Milvus。
- `DocumentRecognizer` 首期由 `PpocrDocumentRecognizer` 实现（mica-ppocr），字段抽取与模板独立于 OCR 引擎。
- `ObjectStorage` 首期由 `S3ObjectStorage` 实现（AWS SDK for Java v2），覆盖两端：本地开发 RustFS，线上 Cloudflare
  R2；业务层不直接依赖 S3 SDK，对象键带租户前缀，仅私有读与短时效预签名。
- `KeyStore` 由 `DbKeyStore` 实现（`face_tenant_keys` + 主密钥包裹，主密钥只走环境变量）；业务层只依赖接口，不感知存储细节。

## 5. 数据与状态

| 存储       | 内容                                          | 生命周期             |
|------------|-----------------------------------------------|----------------------|
| PostgreSQL | 租户、主体、人脸档案、gallery、证件记录、审计 | 按租户策略           |
| pgvector   | 人脸特征向量与索引                            | 随档案删除           |
| Redis      | challenge、jti、限流计数、短期会话            | TTL 自动过期         |
| 对象存储   | 可选原始帧、证件图                            | 复核窗口后删除       |
| 密钥库     | 租户密钥（`face_tenant_keys`，主密钥包裹）    | 长期，按密钥轮换策略 |

会话状态：`Created → Challenging → Collecting → Processing → Passed/Failed/Expired`。档案状态：
`None → Enrolling → Active → Deleting → Deleted`。

## 6. 多租户

- 所有业务表含 `tenant_id`，查询强制过滤；禁止跨租户查询 gallery。
- 每租户独立策略：阈值、帧数、留存、模型版本、配额、回调地址。
- 加密密钥按租户派生；落库由主密钥包裹（主密钥只走环境变量）；密钥不可用时拒绝写入特征，不降级为明文。
- 平台管理员操作与租户调用分开审计，管理员不能读取特征明文。

## 7. 部署约束

- 生产目标 Linux x64/arm64 + glibc（eclipse-temurin 基础镜像）；mica-ai-face 依赖 openpnp OpenCV，提供 macOS/Windows/Linux
  原生库，本地开发可在 macOS 直接跑真实引擎。
- 模型与原生库只读挂载，启动校验 sha256。
- ONNX 推理占用 CPU，使用有界队列削峰并按实例横向扩容；不追求单进程高并发。
- API 与 Worker 可独立扩缩容；数据库连接池与 ONNX 会话数需设上限。

## 8. 非目标

- 不提供业务用户登录、账户体系或业务放行逻辑。
- 不验证证件真伪（全息、UV、纸张纹理等）。
- 首期不做跨租户 1:N、不做大规模人脸库检索。
- 不替代持牌实名渠道；平台定位为内部风控与 KYC 辅助能力。

## 9. 与现有系统关系

`cpay-api` 现有的 0006 人脸认证是“上传照片 + 后台人工审核”；本平台是自动活体与比对能力服务，接入后可作为该流程的前置自动核验，但两者不共享实现，需通过接口集成。
